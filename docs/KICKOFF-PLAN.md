# Golf Operations 项目启动与验收计划

日期：2026-11-22。下列排程和指标是建议目标，未通过真机/网络测试的项目不视为交付。

## 启动目标

先做一个可复用的行动核心，用接机换车作为第一条验证链路，同时从第一周验证语音和 ATAK。试点最终要能观察到：工作人员报告车辆故障；指挥员看到原音、转写和关联的球员/行程；系统给出有依据的候选；授权调度产生任务；接收人员收到并明确确认；球员实际转移、抵达、交接分别确认。

本包完成的是该链路的本机文字与数据库部分。地图、外部数据、通信、设备投递和 AI 仍有独立验收门槛。

## 第一阶段范围

- 服务链：接机 → 会合 → 登车 → 饭店交接。比赛接送和后续服务沿同一模式扩展。
- 角色：调度员、接待员/司机；后续按任务而非应用版本扩展。
- 场地：一个机场集合点、一家饭店、一段接送路线，全部以实际活动数据导入。
- 设备：现有指挥电脑与 2–3 部 Android 手机，其中一部安装 ATAK；耳机可用现有设备。
- 通信：一个试点频道、真实 PTT、一条持久消息时间线、一路按需视频。
- Ontology：高尔夫正式用例；会议作为同一应用复用的独立反例测试。
- 外部信息：先接真实航班状态、车辆 GPS、一条路线和与球场有关的天气。AIS、全球新闻、World Monitor 聚合进入后续列表。

## 模块边界与选型

| 层 | 起步选择 | 边界 |
| --- | --- | --- |
| Web 指挥台 | 本包为无构建依赖的 HTML/CSS/JS；团队进入产品开发可迁至 React/TypeScript | 能力契约稳定；界面不绑定高尔夫类型 |
| Staff App | 受控业务原型先用本包浏览器视图；现场语音优先 Android 原生或含原生服务的应用 | PTT/后台不能仅凭 Web 演示通过 |
| Ops API | Python FastAPI，模块化后端 | API 模块、Handler、适配器边界先清楚，不先拆大量微服务 |
| 正式数据层 | PostgreSQL + PostGIS；对象、关系、观测、证据、行动与审计分层 | SQLite 仅本包本机验证；时空查询、全局资源预留和迁移另做 |
| 通信 | 自托管 LiveKit / WebRTC + 服务端 PTT 话权 | SFU 负责媒体；持久消息、业务权限、话权仲裁由本系统负责 |
| 音视频归档 | 可自托管的 S3 兼容对象存储，依据最终许可证/团队能力选型 | 单句音频/视频文件与业务数据库用证据引用关联 |
| TAK | OpenTAKServer + 独立 CoT Adapter | 现场试点通过 OpenTAKServer 收发 CoT。官方 WebTAK 兼容性单独验证 |
| AI Worker | 可替换的 ASR、提取、摘要、建议生成器 | 只访问授权证据；无数据库任意写权限；不能当作 PTT 必需路径 |
| Action Runtime | 鉴权、前置条件、版本、幂等、事务、outbox、投递与回执 | 以已授权 Action 为执行入口，AI 输出不能绕过它 |
| 运行设施 | 测试机与 Compose 起步、集中日志/指标/备份 | 先量测，再决定拆服务、扩容和多地域 |

正式身份可使用已有 OIDC 提供方或团队可自托管方案，接入活动成员、角色与设备关系。客户端不提交可信角色；服务端根据身份计算允许行动，执行时再次检查。

## Ontology 复用契约

不同活动允许拥有不同 Ontology。应用只依赖能力接口，例如 WorkItem、Locatable、Journey、CollaborationSpace、Evidence 与 ActionDescriptor。一个 Binding 应包含查询/过滤/分页、关系遍历、事件订阅和领域 Action 映射，不能只把字段名称改成一套固定高尔夫 Schema。

应用读取 event_id、ontology_id、schema_version、binding_version、view_version。对象版本只表示某个实例状态。事件实例与模板分开；新建活动只复用模板和定义，不复制历史聊天、分配、回执或已完成事实。车辆/人员的全局身份与各活动的时间窗预留分开维护，避免下一场活动重复建人和重叠预留车辆。

本包只实现了最小任务投影、候选关系读取与两种领域行动映射。完整查询 DSL、可视化建模、事件订阅、跨版本迁移仍在后续队列。

## PTT、视频、文字的具体交付边界

话权控制器维护频道、持有人、lease、过期时间、优先级与撤销原因。服务端授予有效话权后才允许发布音频，异常断线后释放。测试同时按下、网络中断、旧客户端重连和权限变化。需要防止客户端绕过 UI 直接持续发布。

语音与视频的发布权限不能粗暴共用一个总开关：撤销发言权时应避免停止正在观看的视频。具体使用发布源权限或音频/视频房间与身份分离，以 SDK 和服务端实测为准。一个操作者多屏时只有一个音频控制端，副屏默认静音。

一段 PTT 发言生成一个 message_id。原音、初步转写、最终转写和修订关联同一条记录；重连补取历史依靠业务消息存储。离线录音标注为待上传语音留言，不能重连后自动作为实时 PTT 播出。视频按需开启，默认不另开第二路麦克风。

ATAK 第一阶段只做地理态势与事件互通。专业用户在同一支手机使用 ATAK + Staff App 语音，无需新增手机。原生 ATAK 内嵌 PTT/视频插件是独立工作项，要验证 SDK、版本、签名、用户交互和音频焦点，不把它含糊地算进“TAK 已接入”。

## 动态感知与执行结果

GPS、天气、航班、人员汇报首先进入 Observation/Evidence，记录 source、observed_at、received_at、valid_until、单位/坐标系和质量信息。经过对象关联与规则/人工确认后才改变业务事实。车在饭店范围内只能说明位置满足条件，不足以证明球员下车、酒店接手或入住完成。

Action 状态至少区分：系统已提交、投递中、终端已收到、人员已接单、现场已完成、失败。投递重试与现场补偿是明确行动，不能用重复数据库写入假装补偿。系统崩溃后依据 outbox 和幂等键恢复发送；超时要给调度员明确状态，不自动伪造成功。

## 第一轮建议验收门槛

下面均为拟定目标，不是本包实测性能或 LiveKit 官方保证。

| 项目 | 受控测试目标 |
| --- | --- |
| 应用复用 | 同一前端构建跑高尔夫和会议场景；变更 Binding/配置，不增领域类型判断 |
| 汇报与执行 | 普通文字/语音和 AI 建议都不能直接写已执行事实；授权 Action 才能改变业务状态 |
| 幂等 | 同一请求重放 10 次仅一个逻辑提交；同 key 不同 payload 拒绝；竞争预留只一个成功 |
| 消息历史 | 100 条混合记录，重启和断线重连后完整；音频和转写不重复建消息 |
| 话权 | 100 轮双端竞争同频道，不出现两个有效发布者；失联后在配置 lease 时间内释放 |
| 语音延迟 | 在记录清楚的稳定网络上，按键到允许发言 P95 ≤ 500ms，授权后单向语音 P95 ≤ 500ms；分别量测 |
| 网络切换 | 10 次 Wi-Fi/移动网络切换，恢复目标 ≤ 10 秒；状态可见，离线语音不自动实时补播 |
| 锁屏 | 每台试点手机连续 30 分钟接收与经明确用户操作发言；失败系统版本排除试点 |
| 转写 | 30 条含姓名、车辆号、地点的语音人工检查；关键对象不明时必须待确认 |
| TAK | 实机移动 10 分钟，组内点位正确，组外不可见，过期标明陈旧，回流不增殖。中台发出的试点事件能在 OpenTAKServer 回读同一 CoT UID |
| 视频 | 一路手机视频持续 10 分钟且 PTT 可用；不把一路成功推导为最大人数 |
| 全链路 | 原音/文字 → 来源明确的建议 → 授权提交 → 实际终端接收 → 人员接单 → 现场确认均有独立证据 |
| 故障 | AI 或外部数据源中断不影响人工 PTT/文字调度；业务核心故障有人工备用流程 |

性能报告记录版本、手机、网络 RTT/丢包、服务硬件、编解码、码率、同时在线与同时发布数，以及样本数量。需要按业务同时发言/视频组合压测，不能只用平台注册人数宣称容量。

## 后续阶段

- 第 3–4 周：完成一组人员的受控试点，扩展接机/酒店交接的状态模型与断线恢复，处理前两周真机阻断项。
- 正式活动前：覆盖球员全旅程、异常处置、班次与权限、恢复演练、数据备份/恢复、设备版本清单、运维值守和培训。
- 跨活动平台：把新场景接入变成版本化 Ontology + Binding + 视图/规则包；增加跨活动资源预留与兼容性检查，保持同一 App。

先前讨论的 12–16 周正式活动 MVP 只适用于约 5–6 位有经验成员、范围稳定且数据/设备接入及时的估算。现在先用两周实测修正该估算，不将原始时间预估当作已经承诺的上线日。

## 实施前需要提供的真实信息

1. 最近一次计划用于试点的活动日期、城市、球员/工作人员/车辆数量，人数未定可先给范围。
2. 试点工作人员手机的 Android/iOS 构成、型号、系统版本，是否已有 ATAK。
3. 现有开发成员与技能；已有代码仓库、测试机和域名。无现有仓库时以本包新建独立项目。
4. 一份去除不必要个人资料的球员行程、车辆和班次样表，以及一个实际异常处置例子。

这些信息用于安排联调，并不影响先运行本地原型。只有看到真实代码后才决定复用其他已有系统，不假设已有 Ontology/Runtime 能直接满足本项目。

## 一手参考与事实边界

- [LiveKit 本地运行](https://docs.livekit.io/transport/self-hosting/local/)：支持本地启动；不自动产生业务 PTT 控制器。
- [LiveKit 文字流](https://docs.livekit.io/transport/data/text-streams/)：长期历史需自行持久化。
- [LiveKit 部署](https://docs.livekit.io/transport/self-hosting/deployment/) 与 [端口](https://docs.livekit.io/transport/self-hosting/ports-firewall/)：跨设备联调需要正确 TLS、ICE 与 TURN 配置。
- [Android 后台服务限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)：麦克风前台服务受 while-in-use 权限与后台启动规则约束。
- [官方 TAK Server](https://github.com/TAK-Product-Center/Server) 与 [OpenTAKServer 功能说明](https://docs.opentakserver.io/)：以实际选用服务端与 ATAK 版本测试证书、群组和 CoT。

架构、时间和验收目标是本项目建议；上述文档支持具体产品行为，不代表上游保证本项目端到端性能。
